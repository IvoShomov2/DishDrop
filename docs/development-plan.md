# План за разработка

Този план разделя фактическата техническа основа, училищния Етап 1, предстоящата начална работеща версия и бъдещите идеи. Източниците са двата Word документа от 16.11.2026 г.; [спецификацията](project-specification.md) ги пренася с критерии за приемане. Планирана задача не разрешава реализацията на целия списък.

## Фактическо състояние на кода

Прегледан изходен commit: `4d46cd3` на main, merge на PR #2. Документационната задача работи в `docs/simplified-project-scope` и не променя кода.

| Област | Налице в репото | Какво не следва от това |
| --- | --- | --- |
| Структура | Един net10.0 solution, Web/Core/Data и двата тестови проекта с настоящите references | Няма услуги в Core; Services още не съществува |
| Web | Home/Privacy/Error, Identity Register/Manage, традиционен Program.Main | Няма ресторантски/куриерски/admin бизнес панели или checkout |
| Identity | ApplicationUser, стандартни роли, уникален email, RequireConfirmedAccount=true | Register още не дава Customer; няма забрана Restaurant + Courier или завършено IsActive/session блокиране |
| Persistence | Широк модел със staff, менюта, варианти/опции, histories, reviews/support/notifications/audit | Новото опростяване не е приложено; entities/enums не са услуги |
| Схема | Две миграции, snapshot, идемпотентен SQL script, DB описание и ER диаграми | Приложната development база е непотвърдена без отделна проверка |
| Seeding | Изричен reference/demo seeder, ownership guard и rollback тестове | Още използва Демоград, staff, два ресторанта на един owner и варианти; не е новият начален обхват |
| Тестове/CI | HTTP/Identity, metadata и disposable SQL Server тестове, отделни CI jobs | UnitTests няма бизнес тестове; няма coverage на бъдещите услуги |

В тази Markdown задача не са изпълнявани build, тестове, CI, migrations или DB connection. Предходни резултати не се записват като текущо успешно изпълнение и тук не се поддържа остарял брой тестове. Предишният план сочи исторически [CI run за commit 45bdd38](https://github.com/IvoShomov2/DishDrop/actions/runs/43653724491); той не доказва резултат за днешния branch и не е проверяван сега.

## Предстояща начална работеща версия

Всяка задача се възлага поотделно. Критериите по-долу допълват REG/CUSTOMER/OWNER/CATALOG/CHECKOUT/STATUS/DELIVERY/PAYMENT-HISTORY/ADMIN/DELETE от спецификацията, без разширяване на продукта.

### Подготовка и промяна на модела

| Задача | Зависимост | Критерий за приемане |
| --- | --- | --- |
| S1. Решения и разрешена инвентаризация | Преди новия модел | Отговори на Q3–Q6; конкретна база, backup/restore и конфликти при owners/роли/варианти/такси/райони/истории. Без автоматично изтриване. Q1/Q2 се решават преди съответните услуги. |
| S2. Одобряване на target и mapping | S1 | Точен списък таблици/полета/constraints, source→target map за всеки конфликт и retention политика; примерните имена не са генериран код. |
| S3. Подготвителен expand/backfill | S2 и отделно възлагане | Одобрени ownership, geography, catalogue/fee връзки без загуба на старите данни; конфликтите спират с диагностика. |
| S4. Количка, snapshots, статуси и contract | Проверен S3 | Одобрена cart политика; запазени account IDs, snapshots, суми, получени пари и histories; новите ограничения са SQL-проверени; премахване само след одобрен пренос/архив. |
| S5. Seeder, upgrade тестове и фактически DB docs | S3/S4, координирано с тях | София/24 официално сверени района, валиден owner–restaurant demo модел без Employee/варианти; secrets извън Git; repeat/rollback/ownership и legacy upgrade проверки; актуализирани script и реални ER диаграми след прилагане. |

Подробностите са в [database-change-plan.md](database-change-plan.md). S3–S5 могат да се разделят на повече малки миграционни задачи, но не се прилагат частично несъгласувани schema/service промени.

### Бизнес услуги и MVC интерфейс

| Задача | Зависимост | Критерий за приемане |
| --- | --- | --- |
| F1. Регистрация и клиентски профил/адреси | Одобрен account/address модел, Q4 | REG/CUSTOMER: Customer права, уникален email, deferred confirmation без EmailConfirmed=true; собствени данни; FormModels отделени от entities. |
| F2. Кандидатури и административни одобрения | F1, ownership/courier модел, Q3 | Същата заявка след отказ; причина; права само след одобрение; забранени комбинации и конкуренция се проверяват при кандидатстване/одобрение. |
| F3. Собствен ресторант, график и покритие | F2 и одобрена география | OWNER/CATALOG-EDIT: информация/URL, един дневен интервал или почивен ден, обща неотрицателна EUR такса, временен stop, без минимум; чужди IDs се отказват. |
| F4. Категории/ястия и изтриване | F3, Q4/Q5 | Една цена, свободен текст за количество, наличност, URL; DELETE правила, празни категории, ordered dish деактивиране и обработени cart връзки. |
| F5. Публичен каталог | F3/F4 | CATALOG-VIEW: район, име и категории; правилна видимост за затворено/временно спряло/административно спряно; без cuisine/rating филтри. |
| F6. Количка | F1/F4/F5 | Един ресторант, потвърдено изчистване при смяна, 1..99 и премахване; без авторитетни цени/резервации. |
| F7. Checkout и snapshots | F6, изрично Q1 | CHECKOUT: повторна server проверка, потвърдена промяна на цена/такса, отказ за неналично ястие/чужд адрес, без дубликати/частични записи. |
| F8. Собственик обработва поръчки | F7 | STATUS: приемане/отказ с причина, последователно Preparing/Ready, само свои поръчки; без редакция на изпратеното съдържание. |
| F9. Courier покритие, поемане и освобождаване | F2/F8, изрично Q2 | DELIVERY: лични данни след поемане, само Ready/free/allowed area, един активен assignment, атомарна конкуренция; освобождаване с причина само преди вземане. |
| F10. Вземане, доставяне и cash плащане | F9 | Order е във „В доставка“ при вземане; едно действие за Delivered/Paid и collector/time; повторение/частичен failure не поврежда history/пари. |
| F11. Блокиране, спиране и проблемни случаи | F2 и координирано с F7–F10 | ADMIN: прекратени защитени сесии; отделно спиране на Restaurant/Courier запазва Customer; няма автоматична отмяна на текущи операции; Admin решение с причина/плащане. |
| F12. Приемане на началната версия | F1–F11 | Функционални/authorization/concurrency/SQL и ръчни сценарии за всички критерии; чужд достъп, двойно поръчване, състезание за доставка, суми и history са проверени; реалните ограничения/резултати са документирани. |

Всяка F задача реализира само своите услуги с интерфейси в Core и нужните MVC части в Web. Няма предварително генериране на празни услуги/папки или общи абстракции.
