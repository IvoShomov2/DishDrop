# Правила за работа по DishDrop

- Изпълнявай само възложената задача. Планът за бъдещи функции не разрешава реализацията им.
- Работи в отделен branch за конкретната задача. Ако подходящ branch вече е създаден, продължи в него.
- Не прави commit, push или merge без изрична инструкция.
- Променяй само файловете, необходими за възложената задача.
- Не добавяй функции, слоеве, библиотеки, repository framework или общи абстракции без обсъждане.
- При неуточнено продуктово решение попитай. Не превръщай предложение или отворен въпрос в одобрено правило.
- Разграничавай текущ код, договорена начална работеща версия и бъдещо надграждане.
- Продуктовият обхват е в [спецификацията](docs/project-specification.md); отложените идеи са в [future-improvements.md](docs/future-improvements.md).
- Текущата схема е описана в [docs/database.md](docs/database.md) и [docs/database-diagram.md](docs/database-diagram.md). Статусът на предложените промени се следи в [docs/database-change-plan.md](docs/database-change-plan.md); не ги приемай за приложени без проверка на кода и миграциите.
- Запазвай Web/Core/Data и двата тестови проекта с настоящите зависимости. Core не зависи от Web.
- Web съдържа HTTP/UI и ViewModels/FormModels. Услугите с интерфейси са в Core, групирани по функционалност; DB entities, enums, DataConstants и контекстът са в Data.
- Контролерите обработват HTTP и извикват услуги. Бизнес правилата и заявките към DbContext са в услугите. Views показват подадените модели.
- Интерфейсът и реализацията на услугата стоят заедно в `Core/Services/<функционалност>`.
- Не използвай DB entities директно като модели за входни MVC форми.
- Запазвай традиционния стил: namespaces със скоби, традиционни конструктори, четимо оформление, `ICollection<T>` с `new List<T>()`, атрибути и DataConstants в entities, допълнителен Fluent API директно в `OnModelCreating` след `base.OnModelCreating`.
- Не създавай празни папки, услуги или модели само заради примерна структура в документацията.
- Не променяй миграции, данни, secrets или Identity настройки като странична промяна. Не пресъздавай база и не избирай автоматично изтриване на съществуващи данни.
- Проверявай Git статуса и запазвай несвързаните потребителски промени. Не използвай reset/clean/force checkout или автоматичен stash за премахването им.
- Изпълнявай подходящите проверки и отчитай реалните резултати и непроведените проверки. Не представяй schema тестове като реализирани бизнес процеси или coverage на бъдещи услуги.
- При задачи само за Markdown проверявай съдържанието, вътрешните линкове и Git diff; не са нужни build, тестове или DB connection.
- Училищният Етап 1 е концепция и техническа основа, различен от началната работеща версия. Не твърди одобрение или предоставен достъп от/за консултанта без потвърждение.
